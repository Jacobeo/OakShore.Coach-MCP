# 03: Heart-rate zone dumps for cardio Activities

**What to build:** For the non-strength Activities in the listed window, fetch
the heart-rate-time-in-zones response and dump it raw. At minimum a run and a
bike Activity, so the cardio path is validated at the same time as the strength
path and is not left as a second unknown.

Separately, fetch the configured heart-rate zone boundaries once. The boundaries
are per sport profile, and cross-sport comparison built on a single wrong set of
zones would be silently wrong, so the dump needs to show which profile each set
of boundaries belongs to.

Reuse the harness from ticket 01 as-is: same token, same pacing, same abort on
401/403/429. Read-only throughout.

## Outcome

Two more passes in `dump_garmin.py`, on the same `PacedReader` as the list and
`exerciseSets` passes: one `GET` of `/biometric-service/heartRateZones` before
the per-Activity work, then one `GET` of
`/activity-service/activity/{id}/hrTimeInZones` per Activity the ExerciseSet
pass did not take. Cardio is defined as the complement of strength rather than
as a list of `typeKey`s, so no Activity is fetched twice and none is skipped by
an unexpected type.

**Run live from the home machine on 2026-09-22** over 2026-08-05 to 2026-09-22
(`--days 48`): seventeen paced calls, no abort. Eight cardio Activities - seven
`running` and one `indoor_cycling` - each with five zone rows on disk, plus the
one boundaries dump.

**The boundaries are per sport profile, and this athlete has exactly one.**
Read literally, the criterion is not demonstrable from this account, and the
tick above is qualified accordingly. What the dump shows is the shape: the
response is a JSON array and each entry names its `sport`, so the boundaries
are attributed to a profile rather than handed over undifferentiated. This
athlete's array holds one entry - `DEFAULT`, `trainingMethod` `HR_RESERVE`,
five zone floors - because nothing overrides the default, not because the
endpoint hides the distinction. The shape is what matters for spec 03: another
athlete's array could hold several, and code that reads the first entry and
calls it *the* zones would be silently wrong for them.

**Each `hrTimeInZones` row carries its own `zoneLowBoundary`**, and all eight
dumps match the `DEFAULT` floors, so every Activity's zones are identified
rather than assumed. What that implies for the sync - whether the boundaries
call is needed at read time at all - is issue 04's question, not this ticket's,
and the note stops at the observation for the same reason ticket 02's does.

`heart-rate-zone-coverage.md` beside the README records all of this without
Activity identifiers or bpm values, alongside the two notes from issues 01 and
02. It is regenerated by every run and by `--from-dumps`, so no question about
this window needs a re-fetch.

An Activity is attributed to a profile by matching its `zoneLowBoundary` values
against the configured floors, because `hrTimeInZones` names no profile itself.
Two profiles configured with identical floors are reported as ambiguous rather
than resolved to whichever came last - that would be the silent cross-sport
wrongness the boundaries call exists to prevent, and this athlete's single
profile means the branch can only be reached from a test.

Enforcement is unchanged and structural: `PacedReader` can issue nothing but
`GET`, and the four paths named in `dump_garmin.py` are every path the script
can ask for. `fetch_heart_rate_zones` takes no Activity, so it cannot be
per-Activity by construction. `test_dump_garmin.py` covers pacing across the
cardio pass, an abort mid-pass leaving the rest unfetched, dump filenames
naming their Activity and endpoint, that the cardio pass never reaches for the
boundaries, and the ambiguous-profile branch.
